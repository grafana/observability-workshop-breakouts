# Lab 2 - Follow the trail into the database

A new complaint about the `ecommerce` store: product pages *hang* for several seconds before the "You might also like" recommendations appear. It's intermittent, it's slow rather than broken, and it started recently.

A frontend symptom, but this time the trail doesn't stop at the browser. Following it leads through a trace and down into a database, where a single query is quietly bringing the whole experience to a crawl. This lab is about **[Database Observability](https://grafana.com/docs/grafana-cloud/monitor-applications/database-observability/)** - and the exact query-level detail it gives you.

## What this lab teaches

**Database Observability** (GA since April 2026) gives you query-level visibility into MySQL and PostgreSQL - self-managed or managed (RDS, Aurora, Cloud SQL, Azure). Grafana Alloy collects it, with no agent on the database host. You'll learn to:

- find the query that's actually costing you, in a ranked **Queries Overview**,
- tell *why* it's expensive using **Calls**, **Duration**, and **Rows Examined**,
- read an **Explain Plan** and spot a missing index in **Table Schema Details**,
- and use the **Grafana Assistant** to turn that diagnosis into a concrete fix.

You'll enter, as always, from the symptom the user feels - then follow a trace to the responsible query.

:::info Why the database?

Applications spend an enormous amount of their time waiting on the database. A single inefficient query - one that looks harmless in code review - can saturate a DB and slow down *every* request that touches it. Query-level observability is how you find it.

:::

## Instructions

Use the Grafana Cloud stack from the slides. This lab uses the `ecommerce` app and its **orders database**; a scenario is already running.

You have around 20 minutes. Attempt each question first, then open **Show answer**.
