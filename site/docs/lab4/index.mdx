# Lab 4 - Follow the N+1 by its shape

A new application this time: **Grafana Bank**, an online-banking app. The **transaction history** page loads fine, and nothing is erroring. But each load fires more than twenty near-identical database queries. It's fast today, so nothing has alerted. This is a latent N+1: the page works now, but the query count grows with traffic and won't scale.

In this lab you'll lead with **[Traces Drilldown](https://grafana.com/docs/grafana/latest/explore/simplified-exploration/traces/)**, then confirm what you find in **Database Observability**. Traces Drilldown is queryless: you explore by clicking through **Rate / Errors / Duration** and span attributes, with no TraceQL to write. The problem here is an access pattern, an N+1 query. Trace shape reveals that pattern. Single-query metrics miss it.

## Instructions

Use the Grafana Cloud stack from the slides. This lab uses the **banking** app.

:::info The scenario running

A k6 load test drives steady traffic against the banking app. The **`transactionsNPlusOne`** feature flag makes the transaction-history endpoint enrich each transaction row one at a time: one database lookup per row instead of a single batched query. That's the N+1. The page responds quickly with nothing erroring, but a single request fans out into 25+ tiny, near-identical `SELECT m.name, c.name FROM merchants ... WHERE m.lookup_ref = ?` queries.

**It's always on.** Unlike the other labs, the N+1 runs continuously in the banking app, on a steady stream of traffic. Any recent window shows it - there's no incident time to pin.

:::

You have around 20 minutes to work through the questions.

:::

## Question 3: Confirm it in a single trace

**Open one transaction-history trace and expand the DB spans. What query runs, and how many times?**

Aggregates point the way. A single trace confirms it.

<TryIt where="any GET /api/transactions trace in the Slow traces list, then expand the transaction service's db.Query spans and read their attributes." />

<details className="answer-reveal">
<summary>Show answer</summary>

Open a `GET /api/transactions` trace and the transaction service fires the same span over and over: **25-plus `db.Query` repeats**, most only a millisecond or two, with the odd one running longer when its merchant lookup scans more rows. Expand one and the `db.statement` is an identical parameterized lookup:

```sql
SELECT m.name, c.name
FROM merchants m
JOIN categories c ON c.id = m.category_id
WHERE m.lookup_ref = ?
```

One request enriches each transaction row with its merchant and category names, one row at a time. That's the **N+1 query** pattern: every individual query is fast, there are just far too many of them.

**How to find it:**

1. Open the **Slow traces** list and click a `frontend` `GET` trace.

   ![Open a transaction trace from the Slow traces list](/img/lab4/4.4-slow-traces.png)

2. Turn on **Show all spans** and expand the transaction service's repeated `db.Query` child spans under `ListTransactions`.
3. Click one and read its attributes - `db.statement`, `db.system` (`mysql`) - and confirm they're identical across the repeats.

![Repeated identical db.statement in a trace](/img/lab4/4.4-trace-span-detail.png)

</details>

**Find the repeated query. What stands out about its Calls versus its Duration?**

In Lab 2 the culprit rose to the top when you sorted by **Duration**. An N+1 query has the opposite profile.

<TryIt where="the Queries Overview with the MySQL engine selected - search for the table the trace pointed at (merchants) and open the per-row lookup." />

<details className="answer-reveal">
<summary>Show answer</summary>

With the **MySQL** engine selected, search for `merchants` (the table the trace pointed at).

![Queries Overview - MySQL engine, searching for merchants](/img/lab4/4.5-queries-overview.png)

One row comes back: `SELECT m.name, c.name FROM merchants m JOIN categories c ON c.id = m.category_id WHERE m.lookup_ref = ?` (instance `mysql`, database **bankingcustomer**), and its **Calls** count is already in the **thousands**. Queries are normalized, so every per-row execution collapses into this single row. The Calls column names the N+1 right away.

![The merchants query in the list - thousands of calls](/img/lab4/4.5-query-list.png)

Open it and the profile is the mirror image of Lab 2's slow query: **Times Called** in the thousands (this run: ~8,790 in an hour) against an average **Duration** of just a few milliseconds (P99 in the low teens), with **Errors** flat at zero. Each execution is cheap and fast. There are just a huge number of them, and no single one would ever trip a slow-query threshold.

![Query Details - thousands of calls against a few-millisecond duration, zero errors](/img/lab4/4.5-queries-by-calls.png)

**How to find it:**

1. Open **Database Observability** -> **Queries Overview**, then select the **MySQL** engine.
2. Search for `merchants` (the table the trace pointed at).
3. Open the `SELECT m.name, c.name FROM merchants ...` query.
4. In **Query Performance**, read **Times Called** (very high) against the **Duration** panel (a few ms) and **Errors** (zero).

## Question 5: How cheap is each execution?

**Open Query Samples. What does the per-execution timing look like - and what does the panel's own behaviour tell you?**

**Query Samples** tries to plot real individual executions with their durations.

<TryIt where="the Query Samples tab of the query details page." />

<details className="answer-reveal">
<summary>Show answer</summary>

Over a wide range there are so many executions that the individual-sample panel **overflows**. It trips a **"maximum number of series (500)" limit** and can only draw the AVG / P95 / P99 duration trend. That overflow is itself the N+1's fingerprint: a normal query wouldn't generate enough samples to hit it. The trend it does draw sits in a tight, low band of **low single-digit milliseconds**, roughly flat even as the request rate bursts.

![Over a wide range the samples panel overflows, and the duration trend holds in the low milliseconds](/img/lab4/4.6-samples-overflow.png)

**Narrow the range to a few minutes** and the individual samples plot: a **dense band of near-identical fast executions**, most landing around **1-2ms** and packed continuously, with the occasional slower outlier. Click any point to inspect that execution: `User: banking`, `Rows Sent: 1` (a single-row lookup), its CPU time and memory, and a link to the full sample SQL. That uniform, high-volume stream is the N+1: one lookup per transaction row instead of one batched query.

![Query Samples over a few minutes - a dense band of fast executions, with one exemplar's detail](/img/lab4/4.6-query-samples.png)

**How to find it:**

1. On the query details page, open the **Query Samples** tab.
2. If you see a **series-limit error**, **narrow the time range to a few minutes** - the sample volume is what overflows the panel at wider ranges.
3. Read the dense band of samples clustered at a low duration. Click one to inspect its details (`Rows Sent`, CPU, memory) and full query text.

</details>

## Question 6: Why did the database metrics look "fine"? <Badge variant="optional">Optional</Badge>

**Why wouldn't a standard slow-query or DB-CPU alert have caught this?**

<TryIt where="no new screens - compare the Calls and Duration columns you've already seen, and think back to the trace." />

<details className="answer-reveal">
<summary>Show answer</summary>

Each query is fast and cheap, so per-query duration looks healthy and the database isn't CPU-saturated. Nothing crosses a slow-query line. The cost is the round-trip overhead multiplied by 25-plus calls per request - work that accrues in the application, *between* the queries, not inside any one of them. Today it hides in a fast page. As transaction volume grows, that per-row fan-out is where the page falls over.

That's why the trace found it first (it shows the repetition) and Database Observability confirmed it via call count rather than duration. The fix is architectural: fetch the rows in one batched query / JOIN instead of one at a time.

**How to find it:**

1. Compare this query's avg **Duration** (a millisecond or two) with its **Calls** (very high).
2. Recall the trace: the time was the sum of many small spans, plus the overhead between them.

</details>

The Assistant should identify the N+1 pattern - a single request issuing many repeated, identical database queries, each fast but wasteful in aggregate - and recommend batching them into one query / JOIN.

```
The transaction-history request executes the same merchant/category lookup
(SELECT m.name, c.name FROM merchants m JOIN categories c ... WHERE
m.lookup_ref = ?) 25+ times per request - a high call count with a per-call
duration of only a millisecond or two. That's an N+1 access pattern: many round-trips instead of
one query. It isn't slow yet, but it won't scale.
Fix: fetch the lookups in a single batched query or JOIN.
```
