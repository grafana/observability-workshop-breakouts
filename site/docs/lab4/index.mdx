# Lab 4 - Follow the N+1 by its shape

This is a new application: **Grafana Bank**, an online-banking app. The **transaction history** page loads fine, and nothing is erroring. However, each load fires more than twenty near-identical database queries. It is fast today, so no alert has triggered, but this is a latent N+1 problem. The page works now, but the query count grows with traffic, and eventually it will not scale.

In this lab you will start with the Grafana Assistant as an explorer, then confirm what it finds by investigating manually in Traces Drilldown and Database Observability. Traces Drilldown is queryless - you explore by clicking through Rate / Errors / Duration and span attributes without writing TraceQL. The problem here is an access pattern: an N+1 query. Trace shape reveals that pattern in ways that single-query metrics cannot.

## Learning objectives

- Use Traces Drilldown to identify access patterns that metrics alone would miss
- Distinguish between fast-per-query and N+1 patterns by trace shape and call count
- Correlate trace repetition with database metrics to confirm the pattern
- Understand why request-level context matters when using the Assistant

## Instructions

Use the Grafana Cloud stack from the slides. This lab uses the **banking** app.

:::info The scenario running

There is steady traffic against the banking app. The `transactionsNPlusOne` feature flag makes the transaction-history endpoint enrich each transaction row one at a time: one database lookup per row instead of a single batched query. That is the N+1 pattern. The page responds quickly with nothing erroring, but a single request fans out into 25+ tiny, near-identical queries.

It is always on. Unlike the other labs, the N+1 runs continuously in the banking app on a steady stream of traffic. Any recent window shows it, so there is no specific incident time to pin.

:::

You have around 20 minutes to work through the questions.

## Question 4: Verify - Confirm it in a single trace

**Confirm the repeated query. Open one transaction-history trace and expand the DB spans. What query runs, and how many times?**

Aggregates point the way. A single trace confirms it.

<TryIt where="any GET /api/transactions trace in the Slow traces list, then expand the transaction service's db.Query spans and read their attributes." />

<details className="answer-reveal">
<summary>Show answer</summary>

Open a `GET /api/transactions` trace and the transaction service fires the same span over and over: **25-plus `db.Query` repeats**, most only a millisecond or two, with the odd one running longer when its merchant lookup scans more rows. Expand one and the `db.statement` is an identical parameterized lookup:

```sql
SELECT m.name, c.name
FROM merchants m
JOIN categories c ON c.id = m.category_id
WHERE m.lookup_ref = ?
```

One request enriches each transaction row with its merchant and category names, one row at a time. That's the **N+1 query** pattern: every individual query is fast, there are just far too many of them.

**How to find it:**

1. Open the **Slow traces** list and click a `frontend` `GET` trace.

   ![Open a transaction trace from the Slow traces list](/img/lab4/4.4-slow-traces.png)

2. Turn on **Show all spans** and expand the transaction service's repeated `db.Query` child spans under `ListTransactions`.
3. Click one and read its attributes - `db.statement`, `db.system` (`mysql`) - and confirm they're identical across the repeats.

## Question 5: Verify - How does an N+1 look in the Queries Overview?

**Verify from the database side. Find the repeated query the trace showed. What stands out about its Calls versus its Duration?**

In Lab 2 the culprit rose to the top when you sorted by **Duration**. An N+1 query has the opposite profile.

<TryIt where="the Queries Overview with the MySQL engine selected - search for the table the trace pointed at (merchants) and open the per-row lookup." />

<details className="answer-reveal">
<summary>Show answer</summary>

With the **MySQL** engine selected, search for `merchants` (the table the trace pointed at).

![Queries Overview - MySQL engine, searching for merchants](/img/lab4/4.5-queries-overview.png)

One row comes back: `SELECT m.name, c.name FROM merchants m JOIN categories c ON c.id = m.category_id WHERE m.lookup_ref = ?` (instance `mysql`, database **bankingcustomer**), and its **Calls** count is already in the **tens of thousands**. Queries are normalized here - the `?` placeholder means every per-row execution, whatever `lookup_ref` it passed, collapses into this one row. So the fan-out that was spread across dozens of spans in the trace lands in a single number: the Calls column.

![The merchants query in the list - thousands of calls](/img/lab4/4.5-query-list.png)

Open it and the profile is the mirror image of Lab 2's slow query: **Times Called** in the tens of thousands (this run: ~23,574 over three hours) against an average **Duration** of a few milliseconds (P99 around 25ms), with **Errors** flat at zero. Each execution is cheap and fast. There are just a huge number of them, and no single one would ever trip a slow-query threshold.

![Query Details - thousands of calls against a few-millisecond duration, zero errors](/img/lab4/4.5-queries-by-calls.png)

A high call count on its own doesn't prove an N+1 - plenty of healthy queries run tens of thousands of times across just as many requests. What makes this one an N+1 is where those calls come from. Over the same 3-hour window, the transaction endpoint served only about a thousand requests, yet this query ran more than 23,000 times. Divide one by the other and you get roughly two dozen executions per request - the same fan-out you counted in the trace. That is the tell: not the raw call count, but that the calls are concentrated into so few requests.

This is why both views matter. Database Observability shows you a query is unusually busy; the trace shows you *why* - one request firing it 25-plus times. The database can't see request boundaries, so it can't tell an N+1 from honest traffic on its own. The trace supplies the missing context, and the two together name the pattern.

**How to find it:**

1. Open **Database Observability** -> **Queries Overview**, then select the **MySQL** engine.
2. Search for `merchants` (the table the trace pointed at).
3. Open the `SELECT m.name, c.name FROM merchants ...` query.
4. In **Query Performance**, read **Times Called** (very high) against the **Duration** panel (a few ms) and **Errors** (zero).

</details>

## Question 6: Verify - How cheap is each execution?

**Verify the Assistant's claim by looking at individual executions. Open Query Samples - what does the per-execution timing look like?**

**Query Samples** tries to plot real individual executions with their durations.

<TryIt where="the Query Samples tab of the query details page." />

<details className="answer-reveal">
<summary>Show answer</summary>

Over a wide range there are so many executions that the individual-sample panel **overflows**. It trips a **"maximum number of series (500)" limit** and can only draw the AVG / P95 / P99 duration trend. That overflow is itself the N+1's fingerprint: a normal query wouldn't generate enough samples to hit it. The trend it does draw sits in a tight, low band of **low single-digit milliseconds**, roughly flat even as the request rate bursts.

![Over a wide range the samples panel overflows, and the duration trend holds in the low milliseconds](/img/lab4/4.6-samples-overflow.png)

**Narrow the range to a few minutes** and the individual samples plot: a **dense band of near-identical fast executions**, most landing around **1-2ms** and packed continuously, with the occasional slower outlier. Click any point to inspect that execution: `User: banking`, `Rows Sent: 1` (a single-row lookup), its CPU time and memory, and a link to the full sample SQL. That uniform, high-volume stream is the N+1: one lookup per transaction row instead of one batched query.

![Query Samples over a few minutes - a dense band of fast executions, with one exemplar's detail](/img/lab4/4.6-query-samples.png)

**How to find it:**

1. On the query details page, open the **Query Samples** tab.
2. If you see a **series-limit error**, **narrow the time range to a few minutes** - the sample volume is what overflows the panel at wider ranges.
3. Read the dense band of samples clustered at a low duration. Click one to inspect its details (`Rows Sent`, CPU, memory) and full query text.

</details>

## Question 7: Verify - Why did the database metrics look "fine"? <Badge variant="optional">Optional</Badge>

**Understand why a standard slow-query alert wouldn't have caught this. Why wouldn't DB-CPU alerts trigger either?**

<TryIt where="the Queries Overview list - scroll it right to see the Errors, Rate, Rows Examined and Rows Sent columns for the merchants query." />

<details className="answer-reveal">
<summary>Show answer</summary>

Every per-query metric an alert would watch looks healthy: **Duration** ~3ms, **Errors** 0%, a modest **Rate** of ~2 req/s. Each query is fast and cheap, so nothing crosses a slow-query line and the database isn't CPU-saturated.

![The merchants query row - Duration, Errors and Rate all benign, but Rows Examined 5,003 to Rows Sent 1](/img/lab4/4.5-rows-examined.png)

The one column that hints at trouble is **Rows Examined vs Rows Sent** - 5,003 scanned to return 1 - because `lookup_ref` is unindexed and every execution scans the table. But `merchants` is small, so that scan is still cheap, and a duration or CPU alert never sees it. (Hold that thought for the Assistant questions.)

The real cost isn't in any single query. It's the round-trip overhead multiplied by 25-plus calls per request - work that accrues in the application, *between* the queries, not inside any one of them. Today it hides in a fast page. As transaction volume grows, that per-row fan-out is where the page falls over.

That's why the trace found it first (it shows the repetition) and Database Observability confirmed it via call count rather than duration. The fix is architectural: fetch the rows in one batched query / JOIN instead of one at a time.

**How to find it:**

1. In the Queries Overview list, scroll right to the merchants query's **Rows Examined** and **Rows Sent** columns.
2. Note the benign **Duration**, **Errors** and **Rate**, then recall the trace: the real cost was the sum of many small spans, plus the overhead between them.

</details>

## Wrap-up

You started with the Assistant's hypothesis about the N+1 pattern and then manually verified it across three dimensions: the trace (repeated queries, each in milliseconds), the Queries Overview (high call count, low duration), and the Query Samples (dense band of fast executions). By letting the Assistant explore first as an investigator rather than just to apply a fix, you then confirmed or challenged its findings with hard evidence. This is the approach to take with AI in observability: leverage its end-to-end perspective, but always verify with the data you can see.

Across four labs you have used **Frontend Observability**, **Database Observability**, **Kubernetes Monitoring**, the **Knowledge Graph** (Entity Catalog, Entity Graph, RCA Workbench), **Drilldown** for logs and traces, and the **Grafana Assistant**. Each tool is suited to a specific kind of problem, but the pattern is the same everywhere: start from the symptom, pick the right lens, follow the evidence, and work with the AI as a thought partner, not as an answer machine that you must simply trust.
