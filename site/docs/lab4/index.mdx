# Lab 4 - One page, twenty queries

Different application this time: **Grafana Bank**, an online-banking app. The **transaction history** page loads fine and nothing is erroring - but each load quietly fires more than twenty near-identical database queries. It's fast today, which is exactly why nothing has alerted. This is a latent N+1: a scalability cliff hiding behind healthy-looking dashboards.

In this lab you'll lead with **[Traces Drilldown](https://grafana.com/docs/grafana/latest/explore/simplified-exploration/traces/)** - queryless trace exploration where you investigate by clicking through **Rate / Errors / Duration** and span attributes, no TraceQL - then confirm what you find in **Database Observability**. The problem here is an access pattern (an N+1 query), which is the kind of thing trace shape reveals and single-query metrics miss.

## Instructions

Use the Grafana Cloud stack from the slides; this lab uses the **banking** app.

:::info The scenario running

A k6 load test drives steady traffic against the banking app while the **`transactionsNPlusOne`** feature flag makes the transaction-history endpoint enrich each transaction row one at a time - one database lookup per row (an N+1) instead of a single batched query. Expect the page to respond quickly with nothing erroring, while a single request fans out into 25+ tiny, near-identical `SELECT m.name, c.name FROM merchants ... WHERE m.lookup_ref = ?` queries.

**It's always on.** Unlike the other labs, the N+1 behavior runs continuously in the banking app, so any recent time range (the last hour is fine) will show it.

:::

You have around 20 minutes to work through the questions.

Try each question on your own first. The **Show answer** block under each question reveals the walkthrough and screenshots.

:::
